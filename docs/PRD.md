# AI 공감 다이어리 — PRD (제품 요구사항 문서)

- 문서 상태: 초안 (사용자 승인 대기)
- 근거 문서: `docs/PLAN.md`
- 작성 단계: 0단계 (product-manager)
- 표기: **[확정 대기]**는 사용자 확인이 아직 안 된 항목이다. 9장에 모아 둔다.

## 1. 목표

### 1.1 제품 한 줄 소개
오늘 있었던 일을 한 줄로 쓰면, AI가 감정을 분석하고 공감하며 위로해 주는 일기 앱.

### 1.2 목표
1. 부담 없이 하루를 기록하게 한다. 한 줄이면 충분하다.
2. 기록마다 따뜻한 공감 메시지와 감정 분석을 돌려준다.
3. 지난 기록을 돌아볼 수 있게 한다.
4. 일기에 자해·극단적 선택 같은 위기 표현이 있으면, 공감 메시지와 함께 전문 상담 연락처를 안내한다.
5. 사용자는 자기 일기만 볼 수 있다.

### 1.3 성공 기준 (이번 과제 범위)
- 구글 로그인 → 한 줄 일기 쓰기 → 감정 분석과 공감 메시지 → 새로고침 후에도 지난 기록에 남아 있다.
- 다른 계정으로 로그인하면 남의 일기가 보이지 않는다.
- 위기 표현이 있는 일기에서 상담 연락처 안내가 빠짐없이 나온다.
- 배포 주소에서 위 흐름이 처음부터 끝까지 동작한다.

### 1.4 느낌
따뜻하고 편안한 일기장 화면.

## 2. 사용자

| 항목 | 내용 |
|---|---|
| 대상 | 구글 계정이 있고, 짧게 하루를 기록하고 싶은 사람 |
| 로그인 | 구글 계정, Auth.js 사용 |
| 권한 | 로그인한 사용자는 **자기 일기만** 쓰고, 보고, 삭제한다 |
| 비로그인 | 일기 기능을 쓸 수 없고 로그인 화면으로 안내한다 |

사용자 요구
- 쓰기 쉬워야 한다(입력 한 칸, 버튼 하나).
- 반응이 따뜻하고 빨라야 한다.
- 내 글이 AI로 전달된다는 점을 미리 알고 싶다.
- 힘든 순간에는 도움 받을 곳을 바로 알고 싶다.

## 3. 범위

- 범위 안: 5.1의 F1~F7.
- 범위 밖: 5.1 표의 마지막 줄 참고.
- 기술 전제 (PLAN.md 기준)
  - Next.js, 인증은 Auth.js(구글).
  - DB는 `.env`의 `DATABASE_URL`이 가리키는 Supabase Postgres. **`diary` 스키마를 새로 만들어** 저장하고 다른 스키마의 표는 건드리지 않는다.
  - AI는 OpenRouter. 1순위 `nvidia/nemotron-3-ultra-550b-a55b:free`, 실패 시 2순위 `nvidia/nemotron-3.5-super-vl:free`. 키 변수는 `OPENROUTER_API_KEY`.
  - 깃허브 저장소 `ai-empathy-diary-ch7`, Vercel 배포.

추가 사실
- 구글 클라이언트 값(Google OAuth): **아직 없음. 나중에 준비.** 3단계 구글 로그인 단계에서 만든다. 변수 이름만 문서에 쓴다(값은 적지 않는다). 그 전에는 로그인 없이 모의 사용자로 개발한다.

## 5. 기능

### 5.1 우선순위 한눈에 보기

| 번호 | 기능 | 우선순위 | 단계 |
|---|---|---|---|
| F1 | 구글 로그인·로그아웃 (Auth.js) | 필수 | 3 (뼈대는 1) |
| F2 | 한 줄 일기 쓰기·저장 (AI 전달 안내 문구 포함) | 필수 | 2~3 |

| F6 | AI 모델 실패 처리 (폴백, 일기 보존, 공감 메시지 재요청) | 필수 | 2~3 |

### 5.2 기능별 설명과 수용 기준

#### F1. 구글 로그인·로그아웃
설명: Auth.js로 구글 계정 로그인. 로그인하지 않으면 일기 화면과 API를 쓸 수 없다.
수용 기준
- [ ] 로그인 버튼을 누르면 구글 로그인 후 일기 화면으로 돌아온다.
- [ ] 비로그인 상태로 일기 화면이나 API에 접근하면 로그인 화면으로 가거나 401 응답을 받는다.
- [ ] 로그아웃하면 세션이 끊기고 지난 기록이 보이지 않는다.
- [ ] 로그인 세션이 풀리면 안내 후 다시 로그인하게 하고, 작성 중이던 글이 사라지지 않게 한다(가능한 범위).
- [ ] 구글 클라이언트 값은 코드·문서·커밋에 쓰지 않고 `.env` 변수 이름으로만 다룬다.
- 참고: 구글 클라이언트 값은 3단계에서 준비한다. 5단계에서 리디렉션 URI를 배포 주소로 등록한다.

#### F2. 한 줄 일기 쓰기·저장
설명: 한 줄 입력 후 저장하면 일기가 DB에 저장되고 F3·F4가 이어서 실행된다. 입력 영역 근처에 AI 전달 안내 문구를 표시한다.
수용 기준
- [ ] 로그인한 사용자가 텍스트를 입력하고 저장할 수 있다.
- [ ] 빈 입력(공백만 포함)은 저장되지 않고 안내 메시지가 나온다.
- [ ] 최대 글자 수를 넘기면 저장되지 않고 안내가 나온다. 최대 글자 수 제안: 200자 **[확정 대기]**.
- [ ] 입력 화면에 "작성한 일기는 AI 분석을 위해 외부 무료 모델로 전달됩니다." 취지의 안내가 항상 보인다(접거나 숨기지 않는다).
- [ ] 저장된 일기는 작성한 사용자의 것으로만 기록된다.
- [ ] 같은 날 여러 개를 쓸 수 있다(1번 답이 확정되면 그에 맞춘다). 하루 작성 상한(제안 20개)을 넘기면 안내가 나온다.
- [ ] 저장 중에는 버튼이 비활성화되어 중복 저장되지 않는다.

#### F3. 감정 분석과 공감 메시지
설명: 저장된 일기를 AI에 보내 감정(기쁨·슬픔·불안·분노·평온 중 하나), 강도(1~5), 공감 메시지를 받아 저장하고 보여 준다.
수용 기준
- [ ] 결과에 감정, 강도, 공감 메시지가 모두 표시된다.
- [ ] 감정은 5가지 목록 안의 값만 쓰이고, 강도는 1~5 정수다. 목록 밖 값이 오면 오류로 보고 재시도 또는 F6 처리를 한다.
- [ ] 공감 메시지는 한국어이고 따뜻한 말투이며, 진단·처방·훈계를 하지 않는다.
- [ ] 1순위 모델 호출 후 결과가 DB에 일기와 함께 저장되어, 새로고침해도 같은 결과가 보인다.
- [ ] 응답은 구조화된 형태로 받아 파싱하며, 파싱에 실패하면 F6으로 처리한다.
- [ ] `OPENROUTER_API_KEY`는 서버에서만 쓰고 브라우저로 내보내지 않는다.

#### F4. 위기 표현 감지와 상담 연락처 안내 (사용자 안전)
설명: 일기에 자해·극단적 선택 같은 위기 표현이 있으면 공감 메시지와 함께 상담 연락처를 안내한다. 정책은 6장.
수용 기준
- [ ] 위기 표현이 있는 일기를 저장하면 결과 화면에 공감 메시지와 상담 연락처 안내가 **함께** 나온다.
- [ ] 상담 연락처 안내는 지난 기록에서 해당 일기를 다시 볼 때도 나온다.
- [ ] AI가 실패해도(F6) 위기 표현 감지는 AI와 별도로 동작해 연락처 안내가 나온다(6.2의 규칙 기반 감지).
- [ ] 안내 문구는 비난·진단·경고조가 아니고, 도움을 요청해도 된다는 따뜻한 톤이다.
- [ ] 연락처 번호는 6.3의 확정된 목록과 같고, 전화 걸기 링크(`tel:`)가 모바일에서 동작한다.
- [ ] 위기 표현이 없는 일기에는 연락처 안내가 나오지 않는다(과도한 노출 방지). 다만 감정이 모호할 때는 놓치는 것보다 안내하는 쪽을 택한다.
- [ ] QA 4단계에서 위기 표현 시험 문장 세트로 검증한다.

#### F5. 지난 기록 보기
설명: 로그인한 사용자 본인의 일기 목록을 최신순으로 보여 준다.
수용 기준
- [ ] 목록에 작성 시각, 일기 내용, 감정, 강도, 공감 메시지가 보인다.
- [ ] 최신 작성 순으로 정렬된다.
- [ ] 새로고침이나 재로그인 후에도 기록이 남아 있다.
- [ ] 다른 계정으로 로그인하면 남의 일기가 목록에도, 직접 주소 접근에도 나오지 않는다.
- [ ] 기록이 없으면 "아직 쓴 일기가 없어요" 같은 빈 상태 안내가 나온다.
- [ ] 많은 기록은 한 번에 다 불러오지 않고 나눠 보여 준다(한 번에 20개 제안).

#### F6. AI 모델 실패 처리
설명: 1순위 모델이 응답이 없거나(시간 초과), 오류(429 등)이거나, 빈 응답이면 2순위로 넘어간다. 둘 다 실패하면 일기는 저장하고 공감 메시지만 나중에 다시 요청한다.
수용 기준
- [ ] 1순위 실패 시 자동으로 2순위 모델을 호출한다. 사용자에게 모델 이름은 보이지 않는다.
- [ ] 두 모델 모두 실패해도 **일기는 저장된다**(일기 손실 없음).
- [ ] 그 경우 일기에 "공감 메시지 대기" 상태가 기록되고, 화면에 안내와 [다시 받기] 버튼이 나온다(4장 6번 문구 취지).
- [ ] [다시 받기]를 누르면 저장된 일기로 감정 분석·공감 메시지를 다시 요청하고, 성공하면 결과가 저장되어 보인다. 지난 기록에서도 대기 상태 일기에 같은 버튼이 있다.
- [ ] 다시 요청도 본인 일기에만 가능하다.
- [ ] 오류 내용(스택 트레이스, 키, 내부 주소)이 사용자 화면에 나오지 않는다.
- [ ] 각 모델 호출에 제한 시간을 둔다(제안 20초, 구현 단계에서 확정).

#### F7. 일기 삭제
설명: 본인 일기를 삭제한다. 수정은 지원하지 않는다.
수용 기준
- [ ] 각 일기에 삭제 버튼이 있고, 누르면 "정말 삭제할까요?" 확인 절차를 거친다.
- [ ] 확인하면 일기와 그에 딸린 감정·공감 메시지가 DB에서 삭제되고 목록에서 사라진다.
- [ ] 다른 사용자의 일기를 삭제하려는 요청은 거부된다(404 또는 403).
- [ ] 삭제는 되돌릴 수 없다는 점을 확인 문구에 적는다.
- [ ] 수정 버튼이나 수정 API는 없다.

## 6. 위기 표현 안내 정책

### 6.1 원칙
- 안전이 기능보다 우선한다. 위기 표현이 있으면 공감 메시지와 상담 연락처를 **같이** 보여 준다. 연락처만 던지거나 공감 없이 거절하지 않는다.
- 이 앱은 의료·상담 서비스가 아니며, 진단이나 치료 조언을 하지 않는다. 안내는 전문 기관 연결에 한정한다.
- 일기는 평가하거나 막지 않고 정상적으로 저장한다.

### 6.2 감지 방식
1. **AI 판단**: 감정 분석 응답에 위기 여부(예/아니오)를 함께 받는다.
2. **규칙 기반 감지(보조)**: 자해·극단적 선택을 가리키는 표현 목록으로 서버에서 따로 검사한다. AI가 실패하거나 놓쳐도 안내가 나오게 하기 위함이다.
3. 둘 중 **하나라도** 위기로 판단하면 안내한다(놓침 방지 우선).
4. 감지 결과는 일기와 함께 저장해 지난 기록에서도 안내가 나온다.
- 표현 목록과 시험 문장 세트는 ai-integration-specialist가 만들고 qa-engineer가 검증한다. 목록 자체는 문서에 길게 쓰지 않는다.

### 6.3 안내할 상담 연락처 **[확정]**

| 기관·서비스 | 번호 | 용도 |
|---|---|---|
| 자살예방 상담전화 | 109 | 자살 위기 상담 |
| 정신건강 위기상담전화 | 1577-0199 | 정신건강 위기 상담 |
| 청소년 상담전화 | 1388 | 청소년 상담 |
| 긴급 신고(응급) | 119 | 지금 당장 위험할 때 |

- 사용자가 각 기관 공식 누리집에서 위 4개 번호가 맞는 것을 확인했다(확정). 번호는 바뀔 수 있으므로 배포 전에 한 번 더 확인한다.
- 번호는 코드 한곳(설정 상수)에 모아 바꾸기 쉽게 한다.

### 6.4 안내 방식
- 위치: 공감 메시지 바로 아래에 눈에 띄는 안내 상자.
- 내용: 따뜻한 한두 문장 + 연락처 목록 + 지금 당장 위험하면 119.
- 문구 예시(방향): "많이 힘드셨군요. 혼자 견디지 않으셔도 괜찮아요. 이야기를 들어 줄 분들이 있어요."
- 접근성: 색상에만 의존하지 않고, 스크린리더가 읽을 수 있게 한다.
- 일기에 위기 표현이 없는데 사용자가 직접 찾을 수 있도록, 화면 하단에 상담 연락처 링크를 두는 것은 선택 사항으로, 이번 범위에는 넣지 않는다.

## 7. 데이터 항목

저장 위치: Supabase Postgres의 `diary` 스키마(새로 생성). 다른 스키마는 건드리지 않는다. 표와 SQL 초안은 1단계에서 backend-developer가 정한다. 아래는 PRD가 요구하는 **항목**이다.

| 항목 | 설명 | 규칙 |
|---|---|---|
| 일기 내용 | 사용자가 쓴 한 줄 | 필수, 공백만 불가, 최대 글자 수 제한(제안 200자) |
| 감정 | 기쁨·슬픔·불안·분노·평온 중 하나 | AI 결과 대기 중에는 비어 있을 수 있음 |
| 감정 강도 | 1~5 정수 | 감정과 함께 저장 |
| 공감 메시지 | AI가 만든 한국어 메시지 | 실패 시 비어 있고 "대기" 상태 |
| 작성 시각 | 일기를 저장한 시각 | 서버가 기록, 시간대 포함 저장, 화면에서는 한국 시간으로 표시 |
| 작성자 | 로그인한 사용자 식별값 | 모든 조회·삭제 조건에 사용(서버 코드에서 분리) |
| 위기 표현 여부 | 감지 결과(예/아니오) | 지난 기록에서 안내 재표시에 사용 |
| 공감 메시지 상태 | 완료 / 대기(재요청 필요) | F6에서 사용 |

개인정보 관련
- 일기 내용은 AI 분석을 위해 OpenRouter를 통해 외부 무료 모델로 전달된다(안내 문구로 사용자에게 알림).
- 사용자가 삭제하면 DB에서 지운다. 외부 모델 쪽 보관은 이 앱이 통제하지 못한다는 점을 안내 문구에 반영할지는 2단계 문구 확정 시 정한다.
- 로그·문서·커밋에 일기 내용이나 비밀 값을 남기지 않는다.

## 8. 비기능 요구

- 보안: 사용자별 분리는 서버 코드에서 처리한다(RLS는 8장에서 다룸). `.env`는 깃에 올리지 않고, 문서에는 변수 이름(`DATABASE_URL`, `OPENROUTER_API_KEY`, 구글 로그인 값)만 쓴다.
- 입력 검증: 서버에서 빈 값·길이·형식을 검사한다.
- 성능: 저장 후 결과가 오래 걸릴 수 있으므로 "분석 중" 표시를 보여 준다.
- 접근성·반응형: 모바일과 데스크톱 모두 사용 가능, 키보드 조작, 충분한 색 대비.
- 오류 처리: 빈 입력, 너무 긴 입력, 모델 빈 응답·시간 초과·429, 로그인 풀림에서 사용자 친화적 안내.
