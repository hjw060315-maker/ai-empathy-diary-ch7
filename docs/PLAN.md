# AI 공감 다이어리 — 단계별 작업 계획

오늘 있었던 일을 한 줄로 쓰면, AI가 감정을 분석하고 공감하며 위로해 주는 일기 앱을 만든다.
이 문서는 `.claude/agents`의 에이전트 5개에게 역할을 나눠 맡기는 계획이다.
**이 문서는 계획만 담는다. 사용자가 "계획의 N단계를 진행해줘"라고 할 때까지 코드는 만들지 않는다.**

## 1. 요구 요약 (5W1H)

| 항목 | 내용 |
|---|---|
| 누가 | 구글 계정으로 로그인한 사용자. 로그인은 Auth.js. 사용자는 **자기 일기만** 볼 수 있다 |
| 무엇을 | 한 줄 일기 쓰기, 감정 분석과 공감 메시지, 지난 기록 보기. 일기에 자해·극단적 선택 같은 **위기 표현**이 있으면 공감 메시지와 함께 전문 상담 연락처를 안내한다 |
| 왜 | 부담 없이 하루를 기록하고 따뜻한 반응을 받기 위해 |
| 어떻게 | Next.js. 일기는 `.env`의 `DATABASE_URL`이 가리키는 Supabase Postgres에 **`diary` 스키마를 새로 만들어** 저장한다. 다른 스키마의 표는 건드리지 않는다 |
| AI 모델 | OpenRouter `nvidia/nemotron-3-ultra-550b-a55b:free`를 먼저 부르고, 응답이 없거나 오류가 나면 `nvidia/nemotron-3.5-super-vl:free`로 넘어간다. API 키는 `.env`의 `OPENROUTER_API_KEY` |
| 어디에 | 깃허브 저장소 `ai-empathy-diary-ch7`에 올리고 Vercel에 배포한다 |
| 언제 | 아래 6단계를 순서대로 진행한다 |
| 느낌 | 따뜻하고 편안한 일기장 화면 |

## 2. 사용할 에이전트

| 에이전트 | 맡는 일 | 모델 | 쓰는 단계 |
|---|---|---|---|
| product-manager | PRD로 목표·기능·사용자 요구를 정함 | sonnet | 0 |
| backend-developer | 서버, API, DB, 로그인 | sonnet | 1~3 |
| frontend-developer | 화면, 반응형, 접근성 | sonnet | 2~3 |
| ai-integration-specialist | OpenRouter 연동, 프롬프트 | sonnet | 2 |
| qa-engineer | 기능 시험, 오류 처리 검증, 버그 보고 (코드는 고치지 않음) | haiku | 4 |

## 3. 진행 현황

| 단계 | 이름 | 상태 | 커밋 태그 |
|---|---|---|---|
| 0 | PRD | 완료 | DIARY_00_02 (이 계획과 함께) |
| 1 | 뼈대 | 대기 | DIARY_01_01 |
| 2 | 백엔드·AI·화면 동시 진행 | 대기 | DIARY_02_01 |
| 3 | 통합 | 대기 | DIARY_03_01 |

상태는 단계가 끝날 때마다 `대기 → 진행 중 → 완료`로 바꾼다.

## 4. 단계별 계획

### 0단계 — PRD
- **맡는 에이전트:** product-manager
- **하는 일:** `docs/PRD.md`를 쓴다. 목표, 사용자, 기능 목록과 우선순위, 수용 기준, 위기 표현 안내 정책, 데이터 항목(일기·감정·공감 메시지·작성 시각)을 정한다. 아래 "0단계에서 정할 것"에 답한다.
- **끝났는지 확인:** `docs/PRD.md`가 있고, 기능마다 수용 기준이 있으며, "정할 것" 항목에 모두 답이 적혀 있다. 사용자가 PRD를 읽고 승인한다.

### 1단계 — 뼈대
- **맡는 에이전트:** backend-developer
- **하는 일:** Next.js 프로젝트 뼈대, 폴더 구조, 환경 변수 읽기(`DATABASE_URL`, `OPENROUTER_API_KEY`, 로그인 값은 변수 이름만), **프론트·백엔드·AI가 동시에 일할 수 있게 API 약속**(요청·응답 형태)을 `docs/API.md`로 정한다. `diary` 스키마와 표의 초안 SQL을 쓴다.
- **끝났는지 확인:** 빈 앱이 로컬에서 실행되고, `docs/API.md`에 엔드포인트별 요청·응답 예시가 있다. `.env`가 깃에 올라가지 않는다.

### 2단계 — 백엔드·AI·화면 동시 진행
세 에이전트가 **서로 다른 구역의 파일만** 고쳐 동시에 일한다(파일 덮어쓰기 방지). 기준은 1단계의 API 약속이다.

| 동시에 도는 일 | 에이전트 | 맡는 구역 |
|---|---|---|
| ① 백엔드: API 라우트, `diary` 스키마 생성, 일기 저장·조회(본인 것만) | backend-developer | 서버·DB 코드 |
| ② AI 연동: 감정 분석·공감 메시지 프롬프트, 모델 호출과 폴백, 응답 파싱, 위기 표현 처리 | ai-integration-specialist | AI 호출·프롬프트 파일 |
| ③ 화면: 일기 쓰기, 결과 보기, 지난 기록 목록, 상담 연락처 안내 문구, 반응형·접근성 | frontend-developer | 화면 파일 |

- **끝났는지 확인:** 세 구역이 각자 단독으로 실행·시험되고(AI는 모의 응답, 화면은 모의 데이터로), API 약속과 어긋나는 곳이 없다.

### 3단계 — 통합
- **맡는 에이전트:** backend-developer, frontend-developer (필요하면 ai-integration-specialist)
- **하는 일:** 세 구역을 연결한다. Auth.js 구글 로그인, 로그인한 사용자의 일기만 저장·조회, 실제 DB 저장을 붙인다.
- **끝났는지 확인:** 구글 로그인 → 한 줄 일기 쓰기 → 감정 분석과 공감 메시지 → 새로고침 후 지난 기록에 남아 있음. 다른 계정으로 로그인하면 남의 일기가 보이지 않는다.

### 4단계 — QA
- **맡는 에이전트:** qa-engineer (보고만 하고 코드는 고치지 않음. 고치는 일은 담당 개발 에이전트가 한다)
- **하는 일:** 기능 시험과 오류 처리 검증(빈 입력, 너무 긴 입력, 모델 빈 응답·시간 초과·429, 로그인 풀림), 위기 표현 안내 시험, 다른 사용자 데이터 접근 시험, 코드 리뷰. 결과를 `docs/qa-report.md`에 심각도별로 적는다.
- **끝났는지 확인:** `docs/qa-report.md`의 높음 항목이 모두 고쳐졌고 다시 시험해 통과했다.

### 5단계 — 배포
- **맡는 에이전트:** backend-developer, frontend-developer
- **하는 일:** Vercel에 배포하고 환경 변수를 등록한다. 구글 로그인의 리디렉션 URI를 배포 주소로 등록한다.
- **끝났는지 확인:** 배포 주소에서 로그인부터 일기 저장·조회까지 처음부터 끝까지 동작한다.

## 5. 0단계에서 정할 것 (질문 모음)
계획을 쓰며 정하지 않고 남겨 둔 것이다. PRD 작업 전에 사용자가 답한다.
1. 하루에 일기를 여러 개 쓸 수 있는가, 하루 한 개인가?
2. 감정 분류는 어떤 목록으로 하는가(예: 기쁨·슬픔·불안·분노·평온)? 감정 강도도 보여 줄 것인가?
3. 위기 표현을 감지했을 때 안내할 상담 연락처는 무엇인가(예: 자살예방 상담전화 109, 정신건강 위기상담 1577-0199 등 최신 번호 확인 필요)?
4. 일기 수정·삭제를 지원하는가?
5. AI에게 보내는 일기 내용의 개인정보 처리와 보관 안내 문구가 필요한가?
6. 모델 응답이 두 모델 모두 실패했을 때 사용자에게 보여 줄 안내와 일기 저장 정책(일기는 저장하고 공감 메시지만 나중에 다시 요청)은?
7. 사용자별 데이터 분리를 서버 코드에서만 처리하는가, DB의 행 수준 보안(RLS)도 둘 것인가? (노트상 이번에는 서버 코드에서만 처리하고 RLS는 8장에서 다룸)

## 6. 공통 규칙
- 모든 답과 문서는 한국어. `.env`는 열거나 출력하지 않고 변수 이름만 쓴다.
- 다른 스키마의 표는 건드리지 않는다. 모든 DB 작업은 `diary` 스키마 안에서만 한다.
- 단계가 끝나면 이 문서의 진행 현황 표를 갱신하고 내용별로 나눠 커밋한다.
